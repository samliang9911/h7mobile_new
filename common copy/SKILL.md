<EXTREMELY-IMPORTANT>
YOU MUST READ THE CLAUDE.md FILE BEFORE DOING ANYTHING ELSE.

THIS IS NOT OPTIONAL. THIS IS MANDATORY.

ADDITIONALLY, YOU MUST MAINTAIN TWO DOCUMENTS AFTER EVERY TASK:
- DEVELOPMENT.md — append-only change log (never rewrite history)
- STATE.md — current state, freely revisable (always accurate)
</EXTREMELY-IMPORTANT>

## 核心机制：双文档体系

为避免「频繁更新导致旧记录过时或矛盾」，项目维护两份职责不同的文档：

| 文档 | 职责 | 更新方式 | 目标 |
|---|---|---|---|
| `DEVELOPMENT.md` | 变更日志：记录「发生了什么变更」 | **append-only**，禁止覆盖/重写/删除已有条目 | 完整保留历史 |
| `STATE.md` | 当前状态：描述「系统现在是什么样」 | **可自由修订**（覆盖、重写、重组均可） | 始终准确反映现状 |

**为什么这样分？** 旧记录过时的根因是：把「会变的状态描述」当成「不变的事件日志」来追加，导致同一功能出现多条矛盾描述。分离后：
- 状态变了 → 改 STATE.md（不再追加新条目制造矛盾）
- 发生了变更 → 追加 DEVELOPMENT.md（历史不丢失）
- 旧条目被推翻 → 不删除，加废弃标注（见下）

## 任务开始前的检查清单

### 1. 变更日志 (Change Log) — 写入 DEVELOPMENT.md
- **功能**: 实现或修改了什么功能
- **改动点**: 修改了哪些文件/函数
- **依赖**: 新增了什么依赖或前置条件
- **风险**: 潜在副作用或边界情况

### 2. 实现思路 (Implementation Notes) — 记录决策而非实现
- 为什么选这个方案（对比了哪些替代方案）
- 关键设计决策（如：用递归而非循环的原因）
- ⚠️ 只记录「为什么」，具体实现以代码为准（实现细节会过时，决策原因不会）

### 3. 使用示例 (Usage)
- 最小可运行示例
- 常见错误用法（Negative Examples）

### 4. 待优化点 (TODO)
- 性能瓶颈在哪
- 下一步重构方向

## 操作步骤

### 第一步：读取项目指南
1. 使用 Read 工具读取 `d:\CLAUDE.md`
2. 仔细阅读并理解文档中的所有指导、规则和要求
3. 在工作中遵循 CLAUDE.md 中的所有指令

### 第二步：检查开发文档
1. 检查是否存在 `d:\DEVELOPMENT.md` 与 `d:\STATE.md`
2. **DEVELOPMENT.md**：
   - 如存在，读取理解现有内容
   - **严格遵守追加模式**：后续记录基于现有内容续写，绝对禁止覆盖或重写
3. **STATE.md**：
   - 如存在，读取理解当前状态（这是判断「现状」的依据，不是历史）
   - 可自由修订以反映最新状态
4. 如不存在，准备创建新文档

### 第三步：执行任务
1. 按照计划执行代码变更
2. 记录实现过程中的设计决策
3. 测试功能确保正常工作

### 第四步：更新文档（关键步骤）
1. **DEVELOPMENT.md**：在末尾追加一条变更记录（append-only）
2. **STATE.md**：修订当前状态以反映本次变更后的真实情况（可覆盖旧内容）
3. **废弃标注**：若本次变更使 DEVELOPMENT.md 中某条旧记录失效，在该旧条目追加 `⚠️ [已被 YYYY-MM-DD 变更取代]`，但**不要删除**旧条目

### 第五步：【会话上下文管理协议】
1. 每完成一个功能模块，自动生成该模块的「微型摘要」（功能名+核心接口+关键约束）
2. 将「开发日志」内容同步至文档后，从上下文中清除原始实现细节，仅保留摘要
3. 当上下文累积超过 5 个模块时，将微型摘要合并为「项目状态快照」——该快照应对应 STATE.md 的内容
4. 始终保留的上下文：当前任务目标 + 项目状态快照 + 最近 2 轮的对话细节
5. 被压缩的内容可随时应要求展开还原


## 开发文档管理策略

### 文档位置
- `d:\DEVELOPMENT.md` — 变更日志（append-only）
- `d:\STATE.md` — 当前状态（可修订）
- 目的：变更日志记录历程，状态文档反映现状，二者互补

### DEVELOPMENT.md 续写规则（append-only）
1. **每次任务完成后必须续写**：在文档末尾追加新的变更记录
2. **功能新增**：详细描述新增的功能、实现方式和使用方法
3. **功能修改**：记录修改的原因、改动内容和影响范围
4. **功能删除**：说明删除的原因和替代方案
5. **保持时间顺序**：按时间倒序排列，最新变更在最前面
6. **绝对禁止**：覆盖、重写、删除已有条目
7. **废弃处理**：被后续变更推翻的旧条目，追加 `⚠️ [已被 YYYY-MM-DD 变更取代]` 标注，保留原文

### STATE.md 修订规则（可修订）
1. **目标是「始终准确」**：每次变更后同步更新，反映系统当前真实状态
2. **允许覆盖**：旧状态描述可直接替换为新状态，无需保留旧版本（旧版本在 DEVELOPMENT.md 里有历史记录）
3. **按模块组织**：以模块/子系统为单元，描述职责、关键接口、约束
4. **只记现状**：不记录「什么时候改的」「之前是什么样的」——那是 DEVELOPMENT.md 的事
5. **决策导向**：记录关键约束与设计决策，而非易变的实现细节

### 废弃标注机制
当本次变更推翻了 DEVELOPMENT.md 中的旧记录（如旧方案被替换、旧功能被删除）：
- 在旧条目末尾追加：`⚠️ [已被 YYYY-MM-DD 变更取代，详见当日记录]`
- **不要删除或修改旧条目原文**——历史必须可追溯
- 读者据此跳过过时信息，但仍可查阅历史脉络

## 记录原则：决策导向

从源头减少「会过时的信息」：
- **记录决策**：「为什么选方案 A 而非 B」「约束是什么」——这些是历史事实，不会过时
- **不记录实现细节**：「函数 X 的第 30 行怎么写的」——以代码为准，文档记了就会过时
- **代码是实现的单一事实来源**，文档只记录代码无法表达的东西：决策原因、约束、历史脉络
